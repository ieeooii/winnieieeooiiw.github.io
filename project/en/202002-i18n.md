## Overview

Built an i18n system supporting EN, KO, ZH, JA, ES, and PT for the global B2B platform CLOSET. Built on i18next with language JSON files organized by domain (space, style, account, common, etc.), referenced in components via the `t('key')` hook.

## Key Implementations

### Full Component i18n Coverage

- **Problem**: Hardcoded English text existed in many shared areas including Upload, Multiviewer, Common, LeftMenu, Footer, and BannerResendEmail. i18n JSON files were also written inconsistently across domains.
- **Solve**: Audited all hardcoded text, added keys to language JSONs, and applied them to components. Also refactored list sorting logic (`sort-by-change-order`) to operate language-independently.
- **Result**: Full i18n coverage across the service; established a team convention to verify i18n compliance in new feature PRs

### Language-Specific Layout Bug Fixes
- **Problem**: Spanish (ES), Chinese (ZH), and Japanese (JA) text was up to 1.5–2× longer or shorter than English, causing text clipping and layout breaks in fixed-width containers. Button labels in particular frequently overflowed or wrapped to a new line.
- **Solve**: Applied `overflow: hidden + text-overflow: ellipsis` or switched to flexible `flex` layouts for UI elements prone to long text. Also revised language-specific JSON translations to appropriate lengths for UX.
- **Result**: Consistent UI quality maintained across all languages
- **Insight**: "Build UI only to English specs and it will break every time." After this project, I always account for multilingual text length variations upfront in every UI task.
