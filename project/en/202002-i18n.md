# Building i18n Multi-Language Support (5 Languages)

| Field | Details |
|------|------|
| Company | CLO Virtual Fashion |

## Overview

Built an i18n system supporting 5 languages (EN, ZH, JA, ES, PT) for the global B2B platform CLOSET. Based on `next-i18next`, translation files were organized into domain-specific namespaces, and the system was designed so that language settings — including cookie-based language detection, user profile API integration, and date format locale mapping — are consistently reflected across the entire service.

![Language selection](/images/projects/202002-i18n-language.webp)

## Key Implementations

### Comprehensive Audit of Hardcoded Text and Bulk Translation Key Application

- **Problem**: Numerous hardcoded English texts existed across common layouts (header, footer, left menu) and key areas such as upload and share. The multilingual JSON files were also written inconsistently across domains.
- **Solve**: Conducted a comprehensive audit of all hardcoded text, added keys to language JSON files, and applied them to components. Sorting logic was also standardized to work independently of the language.
- **Result**: Achieved full multilingual coverage across the entire service; established a team convention of checking multilingual support during new feature PRs.

### Namespace Separation by Domain for Bundle Optimization and Key Collision Prevention

- **Problem**: As the service grew, concentrating translation keys in a single file would increase file size and load unnecessary translation data on unrelated pages. Without naming conventions for translation keys, key collisions and duplications were likely.
- **Solve**: Split translation files into domain-specific namespace JSONs such as `common` / `account` / `space` (20+ namespaces). Components selectively load only the needed namespaces via the `useTranslation('namespace')` hook. Plurals are handled using i18next's `_plural` suffix convention, and dynamic value insertion is unified with `{{value}}` interpolation syntax. Translations containing HTML markup are rendered safely without XSS using the `Trans` component.
- **Result**: Translation files split by namespace for bundle optimization and key collision prevention; established a consistent convention of adding keys only to the relevant domain file when adding new features.

### Cookie-Server Dual Storage for Cross-Device Language Setting Synchronization

- **Problem**: If language settings were stored only in client cookies, previous language settings wouldn't persist when logging in from another device. Conversely, storing only on the server meant that non-authenticated users' language selections wouldn't be immediately reflected. Additionally, date display formats differ by language (year-month-day order, separators, etc.) and couldn't be handled with i18next translation keys alone.
- **Solve**: Language changes branch into two paths — unauthenticated users save to cookies only, while authenticated users update cookies and also save to the server via user profile API (React Query mutation). A dedicated hook runs at login to synchronize server-stored language settings to the client. Unsupported language codes safely fall back to English via a utility function. Date formats are managed through a constant map that maps i18n language codes to `date-fns` locale objects, automatically injecting the correct locale into date-related components.
- **Result**: Language settings persist across devices upon login, and date display formats switch consistently when the language changes.

### Flexible Layout Handling for Multilingual Text Length Differences

- **Problem**: In Spanish (ES), Chinese (ZH), and Japanese (JA), text length can be up to 1.5-2x longer or shorter compared to English, causing text truncation or layout breakage in fixed-width containers. Button labels overflowing or wrapping were particularly frequent issues.
- **Solve**: Applied `overflow: hidden + text-overflow: ellipsis` or flexible `flex` layouts to UI elements where text could grow longer. Adjusted translations in language JSON files to appropriate lengths considering UX.
- **Result**: Maintained consistent UI quality across all languages.

## Retrospective

"If you design UI based solely on English, it will inevitably break." Text length differences across languages are much larger than expected, especially impacting buttons, tabs, and fixed-width containers. After this project, I developed a habit of proactively considering multilingual text length variations in all UI design. The namespace-based structure for translation files went beyond simple file size optimization — it served as a team convention that clarified "which domain does this text belong to."
