## 소개

패션 브랜드나 리테일러가 자사 웹스토어에 CLO-SET의 3D 의상 뷰어를 iframe으로 삽입할 수 있는 Embed Viewer 기능이다. 3D 파일(.zpac, .zprj 등), 렌더링 이미지, 터테이블 등 다양한 콘텐츠 포맷을 지원하며, 뷰어 UI·배경색·로고·자동회전 등 세부 옵션을 커스터마이징하고 임베드 URL 또는 iframe 코드로 배포할 수 있다. 기업 고객이 도메인 화이트리스트 기반의 접근 제어 정책을 직접 관리할 수 있도록 설계했으며, MobX 기반 스토어로 복잡한 뷰어 상태를 통합 관리했다.

## 주요 기능

- **멀티 뷰 타입**: 3D · 렌더링 · 터테이블 · 2D 이미지 4가지 뷰 타입 지원
- **옵션 커스터마이징**: 배경색·로고·자동회전·화질 등 세부 옵션 실시간 미리보기
- **두 가지 공유 방식**: 임베드 URL + QR 코드 / iframe 코드 선택 제공
- **도메인 접근 제어**: 기업 어드민이 허용 도메인을 직접 관리하는 Private Embed Viewer
- **플랜별 사용량 제한**: 조회 수 집계 및 초과 시 안내 화면 분기

## 주요 구현

### computed 구독으로 멀티 뷰어 타입 조건부 마운트

- **Problem**: 하나의 Embed URL이 3D / 렌더링 / 터테이블 / 2D 이미지 등 여러 뷰 타입을 지원해야 하는데, 타입마다 렌더링 엔진(WebGL 3D 뷰어 vs 이미지 뷰어)과 데이터 페칭 전략이 완전히 다르다. 파일 타입(CLO 네이티브 / 외부 3D / 이미지)과 뷰 타입이 교차하는 조합을 컴포넌트 내부 조건문으로 처리하면 분기가 비선형적으로 커진다. 또한 뷰 타입이 변경될 때 표시 가능한 옵션 목록(컬러웨이·터테이블 등)도 자동으로 갱신되어야 했다.
- **Solve**: 현재 뷰 타입이 3D인지를 스토어의 `@computed` 값 하나로 판별하여, 뷰어 컨테이너가 이 값만 보고 3D 엔진 컴포넌트와 이미지 뷰어 컴포넌트 중 하나를 조건부 마운트. 뷰 타입별로 활성화할 표시 옵션 목록을 객체 맵으로 선언하고, MobX `reaction()`으로 뷰 타입 변경을 감지해 해당 맵의 값으로 옵션 목록을 자동 교체.
- **Result**: 뷰어 컨테이너는 조건 분기 없이 computed 값 하나만 구독, 뷰 타입 전환 시 표시 옵션도 자동 갱신

### 책임별 스토어 클래스 분리와 독립 reset 설계

- **Problem**: 뷰어 상태(컬러웨이 인덱스, 뷰 타입, 로딩 진행률 등), 표시 옵션(배경색, 로고, 자동회전 등), 공개 플로우 진행 상태가 하나의 클래스에 혼재되면 책임 경계가 불분명해지고, 뷰어 타입 전환 시 초기화 범위를 제어하기 어려워진다.
- **Solve**: 뷰어 코어 상태 / 표시 옵션 / 공개 프로세스 상태를 각각 독립 클래스로 분리하고 메인 스토어가 이를 컴포지션(composition)으로 보유. 각 클래스가 자신의 `reset()` 액션을 갖도록 설계하여 초기화 범위를 클래스 단위로 명확히 제어.
- **Result**: 초기화 범위를 클래스 단위로 독립 제어 가능, 컴포넌트는 스토어 구독만으로 상태 수신

### 뷰 타입별 컬러웨이 전환 대응과 텍스처 품질 최적화

- **Problem**: 뷰 타입마다 컬러웨이 전환 방식이 다르다. 3D 뷰어는 엔진 API로 텍스처를 교체하고, 렌더링/터테이블은 컬러웨이별 이미지 시퀀스를 새로 페치해야 한다. 또한 임베드 환경(외부 웹스토어)은 기기 성능과 네트워크 대역폭을 예측할 수 없어 무거운 고화질 텍스처를 기본 로드하면 안 된다.
- **Solve**: 컬러웨이 변경 액션이 현재 뷰 타입에 따라 엔진 API 호출 또는 이미지 시퀀스 페치 중 하나를 실행하는 분기 처리. 텍스처 품질을 고화질/최적화 두 단계로 제어하고, 반투명 소재(시스루·레이스 등)의 정확한 렌더링을 위한 Depth Peeling 옵션을 별도 토글로 제공.
- **Result**: 뷰 타입에 상관없이 일관된 컬러웨이 전환 UX, 저사양 환경에서도 안정적인 재생 보장

### 쿼리 파라미터 직렬화로 URL 공유 시 뷰어 상태 복원

- **Problem**: 배경색·로고·UI 표시 여부·자동회전·화질·뎁스 필링 등 8가지 이상의 옵션을 URL에 담아야 하는데, 모든 옵션을 항상 포함하면 URL이 불필요하게 길어진다. 반대로 뷰어 페이지에서 쿼리 파라미터를 초기값으로 복원하지 않으면 링크 공유 시 설정이 유실된다.
- **Solve**: `qs` 라이브러리로 직렬화할 때 기본값과 다른 옵션만 포함하는 방식으로 URL 최소화. 뷰어 페이지 진입 시 쿼리 파라미터를 파싱하여 스토어 초기값으로 복원하고, 이후에는 스토어 상태만을 신뢰하는 단방향 흐름 유지. Embed Modal의 실시간 미리보기에서는 옵션 변경 즉시 `@computed` URL이 갱신되어 복사 버튼에 반영.
- **Result**: 임베드 URL 하나로 완전한 뷰어 상태 재현, 불필요한 파라미터 없이 URL 최소화

### 도메인 화이트리스트 기반 Private Embed Viewer 구현

- **Problem**: 엔터프라이즈 고객이 자사 도메인에서만 임베드가 작동하도록 제한하려 하는데, iframe 특성상 클라이언트에서 출처를 검증할 수 없고 서버도 일반 Referer 헤더만으로는 신뢰할 수 있는 출처 검증이 어렵다. 어드민이 허용 도메인을 직접 등록·수정·삭제하는 UI도 없었다.
- **Solve**: 뷰어 데이터 API 요청 시 커스텀 헤더로 임베드 출처 도메인을 서버에 전달, 서버가 화이트리스트 대조 후 차단 여부를 결정. 접근 정책을 "공개 / 비활성화 / 허용 도메인 전용" 세 가지 타입으로 설계하고 어드민 콘솔에 도메인 CRUD UI 구현. 도메인 입력 시 클라이언트에서 형식 검증 후 저장, 서버 응답의 에러 코드(중복·형식 오류)를 받아 해당 항목에 오류 표시. 아직 저장되지 않은 신규 입력 항목은 임시 식별자로 구분하여 취소 시 즉시 제거하는 낙관적 UI 처리.
- **Result**: 허용되지 않은 도메인의 임베드 요청은 서버에서 차단, 어드민이 화이트리스트를 직접 관리하는 완전한 접근 제어 플로우 구현

### HTTP 상태 코드 + 에러 코드 조합으로 차단 사유별 안내 대응

- **Problem**: 임베드 뷰어 조회 수를 플랜별로 제한해야 하지만, 뷰어 내부에서 발생하는 여러 API 요청이 중복 카운트될 수 있다. 또한 사용량 초과로 인한 차단과 도메인 미허용으로 인한 차단이 서버 응답 레벨에서 구별되어야 UI에서 적절히 분기할 수 있다.
- **Solve**: 최초 데이터 페치 시에만 카운트가 집계되도록 플래그로 제어. 서버 응답의 HTTP 상태 코드와 에러 코드를 조합하여 "사용량 초과 / 도메인 차단 / 기타 오류" 세 케이스로 분류하고, 각각 다른 안내 화면으로 분기.
- **Result**: 정확한 사용량 집계, 차단 사유에 따른 명확한 안내 제공

## 회고

"하나의 URL이 다양한 상태를 완전히 재현해야 한다"는 요구사항이 설계 전반에 영향을 줬다. 쿼리 파라미터를 초기화에만 사용하고 이후엔 스토어만 믿는 단방향 흐름으로 정리하면서 구조가 단순해졌는데, 이 원칙은 이후 다른 URL 기반 상태 관리에서도 반복적으로 활용했다. 도메인 화이트리스트 검증처럼 신뢰 경계가 클라이언트-서버 사이에 명확히 존재하는 기능은, 클라이언트에서 아무리 잘 막아도 서버 검증이 전제되어야 한다는 점도 다시 확인했다.
