## 소개

CLOSET API를 외부 시스템에서 호출할 수 있는 Developer 설정 페이지와 Webhook 트리거 UI를 개발했다. API Key 발급·재발급·삭제, 키 마스킹·클립보드 복사, Webhook 이벤트 유형(콘텐츠 업로드·공유·Colorway 상태 변경 등) 선택과 엔드포인트 URL·인증 헤더 등록·수정·삭제 UI 전체를 담당했다. 플랜 기반 기능 게이팅(Enterprise / Premium만 API Token 활성화)도 포함한다. 단순 CRUD를 넘어 **API Key 보안 라이프사이클**과 **Webhook 이벤트 구독 모델**을 UI 레벨에서 어떻게 표현할지가 핵심 설계 과제였다.

## 주요 구현

### API Key 생명주기 관리 — 재발급 UX와 MobX 상태 동기화

- **Problem**: API Key는 발급·재발급·삭제라는 세 가지 상태 전환을 가지며, 특히 **재발급은 기존 키를 즉시 무효화**하는 파괴적(destructive) 액션이다. 외부 시스템이 기존 키로 연동하고 있는 중에 재발급을 실수로 누르면 모든 연동이 즉시 끊긴다. 이 위험성을 UI 레벨에서 충분히 전달하지 못하면 사용자가 결과를 인지하지 못한 채 액션을 수행하는 사고가 발생한다.
- **Solve**: 재발급 버튼에 확인 다이얼로그를 배치하여 "기존 API Key가 즉시 무효화됩니다" 경고를 사용자가 명시적으로 확인하도록 강제. 발급된 Key는 전용 모달에서만 노출하고 화면을 벗어나면 마스킹(`****`) 처리 후 클립보드 복사 아이콘을 제공하여 Key 노출 시간 최소화. Key 목록을 MobX 옵저버블 배열로 관리하고, 재발급 응답 수신 시 해당 항목을 즉시 교체하여 UI와 서버 상태를 동기화. 컴포넌트는 모달 개폐·현재 표시 토큰을 로컬 상태로 관리하고, 스토어 액션 결과를 받아 갱신하는 역할 분리 구조.
- **Result**: API Key 재발급 관련 지원 문의 감소, 사용자가 파괴적 액션 전 결과를 충분히 인지하는 UX 확립

### Webhook 구독 모델 — TypeScript 타입 계약과 입력 유효성

- **Problem**: 이벤트 유형이 여러 개(콘텐츠 업로드 / 공유 / Colorway 상태 변경 등)이고 엔드포인트 URL도 이벤트별로 독립적으로 설정되는 구조였다. 백엔드 API 스펙이 개발 도중 변경되면서 파라미터 구조가 바뀌었고, 기존 구현이 신규 스펙과 맞지 않아 서버에 잘못된 요청을 보내는 문제가 발생했다. 또한 잘못된 엔드포인트 URL이나 불완전한 인증 헤더가 저장되면 Webhook 전송 실패로 이어지지만 사용자는 이를 뒤늦게 인지하는 문제도 있었다.
- **Solve**: Webhook 설정 상태를 전용 MobX 스토어로 분리하고, 이미 등록된 이벤트 타입을 `@computed`로 필터링하여 신규 등록 드롭다운에서 자동 제외(중복 등록 방지). 이벤트 유형·트리거 상태·액션 타입을 TypeScript enum으로, 요청 바디를 인터페이스로 명시 정의하여 스펙 변경 시 컴파일 타임에 오류 즉시 감지하는 타입 계약 수립. 입력 안정성을 위해 HTTPS URL 검증과 인증 헤더 key/value 쌍 완전성 검사를 `useMemo`로 파생하여 조건 불충족 시 저장 버튼 비활성화. 인증 헤더 값은 포커스 아웃 시 마스킹 처리하여 화면 노출 최소화. 각 항목에 원본 스냅샷 필드를 함께 저장하고 현재 입력값과 비교하여 실제 변경이 없으면 API 호출 자체를 차단. 삭제는 API 응답 전 로컬 상태를 먼저 제거하는 낙관적 업데이트로 체감 응답성 향상, 수정은 요청 진행 플래그로 중복 제출 방지.
- **Result**: Webhook 이벤트별 URL 등록·수정·삭제 안정적으로 동작. 이후 API 스펙 변경 시 타입 오류로 즉시 감지 가능한 구조 확립

### API 응답 타입 확장으로 UI 상태 격리

- **Problem**: Webhook 항목별로 요청 진행 중 여부, 인증 헤더 설정 여부 등 UI 전용 상태를 추적해야 했다. 이 상태를 API 응답 타입에 직접 추가하면 API 레이어와 UI 레이어의 책임이 혼재된다.
- **Solve**: API 응답 타입을 확장하는 UI 전용 인터페이스를 별도 정의하여 요청 진행 여부·인증 헤더 설정 여부 등 UI 상태를 분리. 스토어에서 API 응답 수신 시 확장 타입으로 변환하여 항목별 UI 상태를 초기화. 원본 스냅샷 필드(`originUrl`, `originAuthHeaderKey` 등)도 확장 인터페이스에 포함하여 변경 감지 로직을 타입 레벨에서 명시.
- **Result**: API 응답 타입 오염 없이 항목별 UI 상태 독립 관리, API 스펙 변경 시 영향 범위 확장 타입으로 한정

## 회고

Developer 설정 페이지를 개발하면서 "API Key는 단순한 텍스트 필드가 아니라 보안 자산"이라는 관점을 UI 설계에 반영하는 것의 중요성을 배웠다. 재발급처럼 복구 불가능한 액션은 "실행하기 어렵게" 만드는 것이 오히려 좋은 UX다. 또한 Webhook처럼 외부 시스템과의 계약 구조를 UI로 표현할 때는, **서버와 클라이언트가 동일한 타입 계약을 공유해야** 스펙 변경 시 사이드 이펙트를 최소화할 수 있다는 것을 이 작업에서 실감했다. MobX의 `@computed`를 통한 파생 상태 관리와 `runInAction` 패턴은 비동기 흐름에서 상태 일관성을 유지하는 데 특히 효과적이었다.
