# Developer API / Webhook 설정 UI 개발

| 항목 | 내용 |
|------|------|
| 회사 | CLO Virtual Fashion |
| 카테고리 | SaaS |
| 서비스 | CLO-SET |
| 기술 스택 | Next.js, TypeScript, MobX, Emotion, i18next |
| 개발 기간 | 2022.09 ~ 2022.10 |
| 서비스 링크 | style.clo-set.com |

## 소개

CLOSET API를 외부 시스템에서 호출할 수 있는 Developer 설정 페이지와 Webhook 트리거 UI를 개발했다. API Key 발급·재발급·삭제 플로우, Webhook 이벤트 유형(콘텐츠 생성/삭제 등) 선택 및 엔드포인트 URL 등록 UI 전체를 담당했다. 외부 개발자가 CLOSET 데이터와 자신의 시스템을 연동할 수 있는 Developer Experience(DX)의 첫 진입점을 설계한 기능으로, 단순 CRUD를 넘어 **API Key 보안 라이프사이클**과 **Webhook 이벤트 구독 모델**을 UI 레벨에서 어떻게 표현할지가 핵심 설계 과제였다.

## 주요 구현

### API Key 생명주기(Lifecycle) 관리 UI 설계

- **Problem**: API Key는 발급·재발급·삭제라는 세 가지 상태 전환을 가지며, 특히 **재발급은 기존 키를 즉시 무효화**하는 파괴적(destructive) 액션이다. 외부 시스템이 기존 키로 연동하고 있는 중에 재발급을 실수로 누르면 모든 연동이 즉시 끊긴다. 이 위험성을 UI 레벨에서 충분히 전달하지 못하면 사용자가 결과를 인지하지 못한 채 액션을 수행하는 사고가 발생한다.
- **Solve**: 재발급 버튼에 `confirmation dialog`를 두 단계로 배치 — 첫 번째는 "기존 API Key가 즉시 무효화됩니다"라는 경고, 두 번째는 사용자 명시 확인(type-to-confirm 패턴). 발급된 Key는 마스킹(`****`) 처리 후 클립보드 복사 아이콘을 제공하여, Key 값이 화면에 노출되는 시간을 최소화. Key 상태(미발급 / 발급됨 / 발급 중)를 MobX observable로 관리하여 UI가 항상 서버 상태와 동기화되도록 구현.
- **Result**: API Key 재발급 관련 지원 문의 감소, 사용자가 파괴적 액션 전 결과를 충분히 인지하는 UX 확립

### Webhook 이벤트 구독 모델 UI 구현

- **Problem**: Webhook은 "어떤 이벤트가 발생했을 때" "어느 URL로" 알림을 보낼지를 설정하는 구조다. 이벤트 유형이 여러 개(콘텐츠 생성 / 수정 / 삭제 등)이고 엔드포인트 URL도 이벤트별로 다르게 설정할 수 있어야 했다. 백엔드 API 스펙이 개발 도중 변경되면서 파라미터 구조가 바뀌었고, 기존 구현이 신규 스펙과 맞지 않아 서버에 잘못된 요청을 보내는 문제가 발생했다.
- **Solve**: Webhook 설정 상태를 전용 스토어로 분리하여 이벤트 타입별 URL 상태를 독립적으로 관리. API 스펙 변경에 따라 파라미터 구조를 리팩토링하고, 요청·응답 타입을 명시적으로 정의하여 스펙 변경 시 타입 체크로 오류를 컴파일 타임에 잡을 수 있는 구조 수립. URL 유효성 검사 함수 추가로 잘못된 엔드포인트 등록 차단.
- **Result**: Webhook 이벤트별 URL 등록·수정·삭제 안정적으로 동작, 이후 API 스펙 변경 시 타입 오류로 즉시 감지 가능

### 다국어 통합 및 개발자 문서 연결

- 디자인 시스템의 `ConfigProvider`를 통해 Developer 설정 페이지 전체 다국어(6개 언어) 적용
- 외부 API 문서(tutorial 페이지) 링크를 컨텍스트에 맞게 연결하여, 개발자가 설정 화면에서 바로 API 레퍼런스에 접근 가능하도록 구성

## 회고

Developer 설정 페이지를 개발하면서 "API Key는 단순한 텍스트 필드가 아니라 보안 자산"이라는 관점을 UI 설계에 반영하는 것의 중요성을 배웠다. 재발급처럼 복구 불가능한 액션은 "실행하기 어렵게" 만드는 것이 오히려 좋은 UX다. 또한 Webhook처럼 외부 시스템과의 계약 구조를 UI로 표현할 때는, **서버와 클라이언트가 동일한 타입 계약을 공유해야** 스펙 변경 시 사이드 이펙트를 최소화할 수 있다는 것을 이 작업에서 실감했다.
