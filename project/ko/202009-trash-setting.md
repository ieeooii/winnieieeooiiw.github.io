# 휴지통(Trash) — 삭제 항목 복원 기능 React 마이그레이션

| 항목 | 내용 |

## 소개

Company Setting의 Trash 탭으로, 관리자가 삭제된 콘텐츠 항목을 페이지네이션 목록으로 조회하고 다중 선택·일괄 복원하는 기능이다. 삭제 항목 조회, 체크박스 다중 선택·일괄 복원, 변환 오류 항목 선택 비활성화, 완료·오류 상태별 모달 피드백을 포함한다. 복원 완료 후 목록 갱신, 선택 상태 초기화, 모달 피드백까지 일관되게 처리하는 것이 핵심 설계 요소였다. 디자인 시스템의 `Table` 컴포넌트를 **명령형(imperative) ref 패턴**으로 제어하여 선택 해제를 외부에서 트리거하는 방식을 구현했다.

## 주요 구현

### useImperativeHandle ref 패턴으로 복원 후 테이블 선택 상태 초기화

- **Problem**: 복원 완료 후 테이블의 체크박스 선택 상태를 초기화해야 했다. React의 단방향 데이터 흐름에서는 부모 컴포넌트가 자식 테이블의 내부 선택 상태를 직접 조작할 수 없다. prop으로 선택 항목을 전달하는 방식도 있지만, 이 경우 테이블 컴포넌트가 자체 관리하는 체크박스 상태와 외부 상태가 이중화되어 동기화 부담이 생긴다.
- **Solve**: 디자인 시스템 `Table` 컴포넌트가 `useImperativeHandle`로 노출하는 테이블 핸들 ref를 `useRef`로 보유. 복원 완료 시 ref의 선택 해제 메서드를 명시적으로 호출하여 테이블 내부 선택 상태 초기화. 페이지 전환 시에도 동일하게 호출하여 이전 페이지 선택 잔재 방지.
- **Result**: 복원·페이지 전환 후 테이블 선택 상태 깔끔하게 초기화, 테이블 내부 상태와 외부 상태 이중화 없음

### 페이지 이동 시 선택 초기화로 페이지 간 선택 오염 방지

- **Problem**: 삭제된 아이템이 많을 경우 전체를 한 번에 불러오면 API 응답이 느리다. 페이지 단위로 로드하면서 여러 아이템을 선택해 일괄 복원하는 플로우에서, 페이지 이동 시 이전 선택 항목이 남아있으면 다른 페이지의 아이템과 함께 복원 요청이 전송되는 문제가 발생한다. 또한 변환 오류가 발생한 항목은 복원이 불가능하므로 선택 자체를 막아야 했다.
- **Solve**: 현재 페이지·전체 수 등 페이지 정보와 선택 항목 목록을 MobX `@observable`로 관리. 페이지 이동 시 목록 재조회와 선택 상태 초기화를 함께 실행하여 페이지 간 선택 오염 방지. 변환 오류 상태의 항목은 행 단위 선택 불가 조건으로 처리하여 잘못된 복원 요청 원천 차단. 복원 버튼은 선택 항목이 없을 때 `disabled` 처리.
- **Result**: 페이지 간 선택 오염 없이 안전한 일괄 복원 동작, 복원 불가 항목 선택 방지

### next/dynamic 지연 로딩으로 초기 번들 최적화

- **Problem**: 복원 플로우에서 발생할 수 있는 상태가 "로딩 중 / 복원 진행 중 / 선택 없음 / API 오류 / 완료" 다섯 가지로 다양하다. 각 상태마다 다른 모달을 표시해야 하고, 모달을 닫을 때 관련 상태를 모두 초기화해야 한다. 상태 초기화를 각 케이스별로 개별 처리하면 초기화 누락이 발생하기 쉽다.
- **Solve**: 로딩·복원 진행·선택 없음·오류·완료 여부 등 다섯 가지 UI 상태를 MobX `@observable`로 선언하고, 단일 초기화 액션 하나로 전부 리셋. 완료·경고 모달은 `next/dynamic`으로 지연 로딩하여 초기 번들에서 제외 — 오류나 완료 상태는 드문 케이스이기 때문.
- **Result**: 모든 진입점에서 단일 초기화 액션 호출로 상태 일관 리셋, 초기 번들 경량화

## 회고

Trash 기능은 단순해 보이지만 "복원 완료 후 상태를 어떻게 깔끔하게 정리하느냐"가 UX 품질을 결정한다. 테이블 핸들 ref 패턴은 선언적 React 패러다임에 어긋나 보이지만, 테이블처럼 내부 상태를 자체 관리하는 컴포넌트의 선택 초기화를 외부에서 트리거해야 할 때 유용한 탈출구(escape hatch)다. 디자인 시스템 컴포넌트가 `useImperativeHandle`로 적절한 명령형 API를 노출해주어야 이런 제어가 가능하다는 것, 즉 **컴포넌트를 설계할 때 "외부에서 어떤 명령이 필요할지"도 미리 고려해야 한다**는 교훈을 얻었다.
