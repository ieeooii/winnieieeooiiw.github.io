# i18n 다국어 지원 구축 (5개 언어)

| 항목 | 내용 |
|------|------|
| 회사 | CLO Virtual Fashion |
| 카테고리 | ETC |
| 서비스 | CLO-SET |
| 기술 스택 | Next.js, TypeScript, i18next |
| 개발 기간 | 2020.02 |
| 인원 | 프론트엔드 1 (담당) |
| 서비스 링크 | [style.clo-set.com](https://style.clo-set.com) |

## 소개

글로벌 B2B 플랫폼 CLOSET에 EN·ZH·JA·ES·PT 5개 언어를 지원하는 i18n 시스템을 구축했다. `next-i18next` 기반으로 번역 파일을 도메인별 네임스페이스로 분리 관리하고, 쿠키 기반 언어 감지·사용자 프로필 API 연동·날짜 포맷 로케일 매핑까지 언어 설정이 서비스 전반에 일관되게 반영되는 구조를 설계했다.

![언어 선택](/images/projects/202002-i18n-language.webp)

## 주요 구현

### 하드코딩 텍스트 전수 조사 및 번역 키 일괄 적용

- **Problem**: 공통 레이아웃(헤더·푸터·좌측 메뉴)과 업로드·공유 등 주요 영역에 하드코딩된 영어 텍스트가 다수 존재했다. 다국어 JSON 파일도 도메인별로 일관성 없이 작성되어 있었다.
- **Solve**: 하드코딩 텍스트를 전수 조사하여 언어 JSON에 키를 추가하고 컴포넌트에 적용. 목록 정렬 로직도 언어에 무관하게 동작하도록 정비.
- **Result**: 서비스 전 영역 다국어 커버리지 확보, 이후 신규 기능 PR 시 다국어 적용을 체크하는 팀 컨벤션 형성

### 도메인별 네임스페이스 분리로 번들 최적화와 키 충돌 방지

- **Problem**: 서비스 규모가 커지면서 번역 키가 한 파일에 집중되면 파일 크기가 커지고 관련 없는 페이지에서도 불필요한 번역 데이터를 로드하게 된다. 번역 키 네이밍 규칙도 없어서 키 충돌 및 중복이 발생하기 쉬운 구조였다.
- **Solve**: 번역 파일을 `common` / `account` / `space` 등 도메인별 네임스페이스 JSON으로 분리(20개 이상). 컴포넌트에서 `useTranslation('namespace')` 훅으로 필요한 네임스페이스만 선택적으로 로드. 복수형은 i18next의 `_plural` suffix 규칙으로 처리하고, 동적 값 삽입은 `{{value}}` 보간 문법으로 통일. HTML 마크업을 포함하는 번역은 `Trans` 컴포넌트로 처리하여 XSS 없이 안전하게 렌더링.
- **Result**: 네임스페이스 단위로 번역 파일이 분리되어 번들 최적화 및 키 충돌 방지, 이후 신규 기능 추가 시 해당 도메인 파일에만 키를 추가하는 일관된 컨벤션 확립

### 쿠키·서버 이중 저장으로 크로스 디바이스 언어 설정 동기화

- **Problem**: 언어 설정이 클라이언트 쿠키에만 저장되면 다른 기기에서 로그인 시 이전 언어 설정이 유지되지 않는다. 반대로 서버에만 저장되면 비로그인 사용자의 언어 선택이 즉시 반영되지 않는 문제가 있다. 또한 날짜 표시 방식은 언어마다 달라(연월일 순서, 구분자 등) i18next 번역 키만으로는 처리할 수 없었다.
- **Solve**: 언어 변경 시 두 가지 경로로 분기 — 비인증 사용자는 쿠키에만 저장, 인증 사용자는 쿠키 갱신과 함께 사용자 프로필 API(React Query mutation)로 서버에도 저장. 로그인 시점에 전용 훅이 실행되어 서버에 저장된 사용자 언어 설정을 클라이언트에 동기화. 지원하지 않는 언어 코드가 들어올 경우 유틸 함수로 영어(fallback)로 안전하게 폴백. 날짜 포맷은 `date-fns`의 언어별 로케일 객체를 i18n 언어 코드와 매핑한 상수 맵으로 관리하여, 날짜 관련 컴포넌트에서 현재 언어에 맞는 로케일을 자동으로 주입.
- **Result**: 기기가 달라도 로그인 시 언어 설정이 유지되고, 언어 변경 시 날짜 표시 형식도 함께 전환되는 일관된 사용자 경험 확보

### 다국어 텍스트 길이 차이에 대응하는 유연한 레이아웃 처리

- **Problem**: 스페인어(ES)·중국어(ZH)·일본어(JA)에서 텍스트 길이가 영어 대비 최대 1.5~2배 길거나 짧아, 고정 너비 컨테이너에서 텍스트가 잘리거나 레이아웃이 깨지는 현상이 발생했다. 특히 버튼 라벨이 길어서 버튼이 밀려나거나 줄바꿈되는 케이스가 빈번했다.
- **Solve**: 텍스트가 길어질 수 있는 UI 요소에 `overflow: hidden + text-overflow: ellipsis` 또는 유연한 `flex` 레이아웃으로 전환. 언어별 JSON도 UX를 고려한 적절한 길이로 번역 수정.
- **Result**: 전 언어에서 동일한 수준의 UI 품질 유지

## 회고

"영어 기준으로만 UI를 짜면 반드시 깨진다." 언어별 텍스트 길이 차이는 예상보다 훨씬 크고, 특히 버튼·탭·고정 너비 컨테이너에서 영향이 크다. 이 작업 이후 모든 UI 설계에서 다국어 텍스트 길이 변화를 사전에 고려하는 습관이 생겼다. 번역 파일을 네임스페이스로 분리하는 구조는 단순히 파일 크기 최적화를 넘어, "이 텍스트는 어떤 도메인에 속하는가"를 명확히 하는 팀 컨벤션 역할을 했다.
