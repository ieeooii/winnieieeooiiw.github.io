# 디자인 시스템 구축

| 항목 | 내용 |
|------|------|
| 회사 | CLO Virtual Fashion |
| 카테고리 | ETC |
| 서비스 | CLO-SET |
| 기술 스택 | React, TypeScript, Emotion.js, Storybook, Rollup, tippy.js |
| 개발 기간 | 2021.06 ~ 2024.11 |
| 인원 | 프론트엔드 4, 프로덕트 디자이너 2 (번들 최적화 단독 주도, 컴포넌트 개발 참여) |
| 서비스 링크 | 사내 내부 (비공개) |

## 소개

총 네 단계에 걸쳐 디자인 시스템을 구축하고 발전시켰다. 1단계(2021.06 ~ 2022.08)에서는 중복 컴포넌트로 인한 UX 불일치와 번들 사이즈 문제를 해결하며 번들 사이즈 82% 감소를 달성했다. 이후 CLOSET 서비스 전용 컴포넌트 추가(2022.03 ~ 2022.12), 사내 디자인 시스템 v1 공통 컴포넌트 제안·설계(2022.07 ~ 2024.11)를 거쳐, 디자인 시스템 v2 구축(2023.07 ~ 2023.12)에서 Lighthouse 95점을 달성했다.

## 주요 구현 — 번들 최적화 및 기반 설계

### 번들 최적화

- **Problem**: 디자인 시스템 패키지가 CJS 단일 번들로 배포되어, 애플리케이션에서 컴포넌트 일부만 사용해도 전체 번들이 포함됐다. React·Emotion 등 공통 의존성이 패키지 내부에 중복 번들링되어 클라이언트 번들이 2.55 MB까지 증가했고, 초기 JS 로드 사이즈는 398 KB였다.

- **Solve**: 아래 세 가지 축으로 최적화를 진행했다.

  1. **Tree-shaking 활성화**: Rollup을 named exports 방식으로 전환하고 `"sideEffects": false`를 선언해 실제 import된 컴포넌트만 최종 번들에 포함되도록 구성했다. CJS에서 ESM 포맷으로 전환하여 번들러가 정적 분석으로 사용 여부를 판단할 수 있게 했다.

  2. **중복 번들 제거**: Rollup externals 설정에 React·ReactDOM·Emotion 등 호스트 애플리케이션이 반드시 보유한 의존성을 명시하고 `peerDependencies`로 이동시켰다. 패키지를 설치하는 애플리케이션이 단일 인스턴스를 공유하도록 구조를 개선했다. 특히 Emotion은 인스턴스가 두 개 이상 존재하면 CSS-in-JS 스타일이 충돌하는 문제가 있어 `peerDependencies` 전환이 기능 안정성에도 직결됐다.

  3. **측정 기반 최적화**: bundle analyzer로 최적화 전·후 번들 구성을 시각화하여 불필요하게 포함된 모듈을 특정하고, 감소 수치를 검증했다.

- **Result**:
  - 디자인 시스템 번들 사이즈 **82% 감소** (Client: 2.55 MB → 72.66 KB / Node.js: 2.54 MB → 126.01 KB)
  - 애플리케이션 초기 JS 로드 사이즈 398 KB → 185 KB
  - Lighthouse 성능 점수 **95점** 달성

### 컴포넌트 설계 패턴

- **Problem**: 초기 디자인 시스템은 스타일이 컴포넌트에 강하게 결합되어 있어, 서비스마다 미묘하게 다른 디자인 요구사항을 수용하려면 컴포넌트를 복제하거나 props를 무한정 추가해야 했다. 이는 유지보수 복잡도를 높이고 API를 불안정하게 만들었다.

- **Solve**: 두 가지 패턴을 조합하여 확장성과 일관성을 동시에 확보했다.

  1. **Headless 컴포넌트**: 상태 로직과 접근성(ARIA) 처리만 담당하고 스타일은 외부에서 주입받는 구조로 설계했다. 서비스마다 CSS-in-JS의 `css` prop 또는 `styled`로 시각적 표현을 자유롭게 커스터마이징할 수 있다.

  2. **Compound Component 패턴**: 예를 들어 `<Select>`·`<Select.Option>`·`<Select.Group>`처럼 부모-자식 컴포넌트가 Context를 통해 내부 상태를 공유하는 구조로, 컴포넌트 소비자가 레이아웃과 구성을 직접 제어하면서도 상태 동기화는 자동으로 이뤄지게 했다.

  3. **Controlled / Uncontrolled 통일 인터페이스**: 폼 관련 컴포넌트는 `value` prop 존재 여부로 controlled/uncontrolled 모드를 내부에서 자동 분기하여, 간단한 사용처에서는 비제어 방식으로 편리하게, 복잡한 폼에서는 완전 제어 방식으로 사용할 수 있도록 단일 API를 유지했다.

### 디자인 토큰 시스템 구축

- **Problem**: 색상·타이포그래피·간격 값이 각 컴포넌트마다 하드코딩되어 디자이너와 개발자 간 불일치가 발생했다. 피그마에서 색상 이름이 변경되면 코드에서 관련 문자열을 일일이 찾아야 했고, 브랜드 리뉴얼 시 영향 범위를 추적하기 어려웠다.

- **Solve**: 색상·타이포그래피·공간(spacing)·elevation을 TypeScript 객체로 정의한 토큰 파일을 단일 진입점으로 구성했다. ThemeProvider와 연결하여 컴포넌트가 토큰 키로만 스타일을 참조하도록 강제했다. 피그마의 토큰 이름과 코드 상수 이름을 1:1 매핑하는 컨벤션을 팀 내에서 문서화하여 디자이너-개발자 간 커뮤니케이션 비용을 줄였다.

- **Result**: 브랜드 색상 업데이트 시 토큰 파일만 수정해 전체 서비스에 일괄 반영 가능. 다크모드 지원 시 토큰 레이어에서 색상 값만 교체하는 방식으로 대응 비용 최소화.

### 컴포넌트 문서화 환경 구축 (Storybook)

- **Problem**: 컴포넌트 사용법을 코드를 직접 읽어야만 파악할 수 있어 팀 내 컴포넌트 재사용률이 낮았다. 새 컴포넌트를 추가할 때 엣지 케이스를 누락하는 경우가 잦았다.

- **Solve**: Storybook을 활용해 컴포넌트별 props·상태·엣지 케이스를 Story로 명세했다. MDX 포맷으로 설계 의도·사용 지침·prop 설명을 함께 작성했다. Controls 패널을 구성하여 디자이너가 직접 prop 조합을 인터랙티브하게 탐색할 수 있도록 했다. Story 작성 자체가 컴포넌트 API 설계를 재검토하는 테스트 역할을 했다.

- **Result**: 디자인-개발 간 컴포넌트 스펙 불일치 감소. Story 작성 과정에서 엣지 케이스를 사전에 발견하는 효과.

## 주요 구현 — 서비스 전용 컴포넌트

### Tooltip / TooltipMenu

- **Problem**: 서비스 전반에 Tooltip이 필요했는데, 기존에는 각 컴포넌트가 tooltip 라이브러리를 직접 사용하거나 제각각의 방식으로 구현하고 있었다. 사용한 라이브러리(`@tippyjs/react`)는 `visible` prop과 `trigger` prop을 동시에 사용할 수 없다는 제약이 있었다.

- **Solve**: 기반 레이어(`BaseTooltip`)를 먼저 설계하고, 그 위에 일반 툴팁과 메뉴 형태의 툴팁 두 가지 변형을 구현했다. `visible` prop 존재 여부로 controlled/uncontrolled 모드를 내부에서 자동 분기하여 라이브러리 제약을 우회했다. 고정 위치·그림자·z-index 등 서비스에서 실제 필요한 옵션을 props로 노출하고, Storybook 문서화를 함께 작성했다.

- **Result**: 서비스 전체에서 일관된 Tooltip UX 제공, 라이브러리 직접 사용 중복 제거.

### 드롭다운 기반 컴포넌트 설계

- **Problem**: 드롭다운 선택 UI가 필요한 컴포넌트마다 열림/닫힘 상태 관리·위치 계산·외부 클릭 감지 로직을 각자 구현하고 있어 코드 중복이 심했다. `display: none`으로 숨길 경우 드롭다운이 닫힐 때마다 DOM 레이아웃이 재계산되어 성능에 영향을 주는 문제도 있었다.

- **Solve**: 드롭다운 컨테이너와 드롭다운 패널을 분리 설계했다. 숨김 상태에서 `display: none` 대신 `width: 0; overflow: hidden`으로 처리하여 DOM에 유지하면서 레이아웃에 영향을 주지 않도록 했다. 기존 카테고리 필터 컴포넌트를 이 컴포넌트 기반으로 마이그레이션하고, 공통 스타일을 별도 모듈로 추출해 이후 Select 계열 컴포넌트가 공통 레이어 위에 쌓이는 구조를 확립했다.

- **Result**: 드롭다운 관련 로직 중앙화. 이후 신규 Select 계열 컴포넌트 추가 시 기반 컴포넌트 위에 쌓는 방식으로 개발 속도 향상.

### Thumbnail (Lazy Load + ratio)

- **Problem**: 콘텐츠 목록·라인시트 썸네일 등 서비스 전반에서 이미지를 사용하는데, 각 사용처마다 lazy load 로직과 비율(ratio) 처리를 따로 구현하고 있었다. 이미지가 로드되기 전 빈 공간이 레이아웃 시프트(CLS)를 일으키는 문제도 있었다.

- **Solve**: `IntersectionObserver`로 뷰포트 진입 시점에만 이미지 src를 set하는 커스텀 훅을 개발하여 Thumbnail 컴포넌트에 내장했다. `ratio` prop으로 `aspect-ratio` CSS를 동적 적용해 이미지 로드 전후 레이아웃 시프트를 제거했다. 이미지 로드 전 스켈레톤 UI를 표시하는 옵션도 추가했다.

- **Result**: 이미지 lazy load와 CLS 방지를 한 컴포넌트에서 처리, 중복 구현 제거.

### 아이콘 컴포넌트 추가

서비스 도메인에 특화된 아이콘(라인시트, 컬러웨이, 순서 변경, 정렬, 복사, QR 등)을 디자인 시스템에 추가했다. SVG를 React 컴포넌트로 변환하여 `size`·`color` props로 제어 가능하게 설계하고, 이미지 파일 의존성을 제거했다.

## 주요 구현 — 공통 컴포넌트

### Skeleton 컴포넌트

로딩 상태에서 빈 화면이나 단순 spinner를 보여주는 방식이 사용자 경험에 좋지 않다고 판단해 직접 제안한 작업이다.

- **Problem**: Skeleton 컴포넌트가 전무하여 로딩 상태를 빈 화면 또는 spinner로만 처리하고 있었다. 각 화면마다 로딩 UI 구현 방식이 달라 일관성도 부족했다.

- **Solve**: 기반 Skeleton 컴포넌트를 Headless 구조로 설계하고 다음 세 가지 확장 메커니즘을 구현했다.

  1. **Props 조합**: `shape(rectangle/circle)`, `variant`, `animation(wave/pulse/false)` props를 조합해 다양한 형태를 단일 컴포넌트로 표현하도록 설계했다.

  2. **`:empty` CSS selector 활용**: 자식 요소가 `undefined`, `null`, `boolean` 등 렌더 결과물이 없는 값일 때 `:empty` CSS pseudo-class가 매칭되는 원리를 활용해, 데이터가 없을 경우 별도 조건 분기 없이 자동으로 스켈레톤 UI가 노출되도록 구현했다.

  3. **Context 기반 일괄 제어**: Context Provider로 특정 영역 단위의 animation 기본값을 일괄 제어하여, 페이지 레벨에서 전체 로딩 애니메이션을 한 번에 켜고 끌 수 있게 했다.

- **Result**: 여러 서비스에 실제 적용. 이후 다양한 Skeleton 요구사항에 구조 변경 없이 대응 가능.

### FileExtension 컴포넌트

- **Problem**: 파일 확장자 표시를 각 서비스에서 각자 구현하고 있어 표현이 제각각이었다. 지원 확장자 목록 유틸이 컴포넌트별로 분산 관리되어 정책 불일치가 발생했고, 신규 포맷이 추가될 때마다 여러 파일을 수정해야 했다.

- **Solve**: FileExtension 컴포넌트를 신규 개발하고, 확장자 타입 분류·아이콘 매핑·미지원 포맷 fallback 처리를 하나의 컴포넌트로 통합했다. 확장자 목록을 단일 소스(Single Source of Truth)로 구성하여 신규 포맷 추가 시 한 곳만 수정하면 전체 서비스에 반영되는 구조를 만들었다.

- **Result**: 서비스 전반에서 파일 확장자 표현 일관성 확보. 신규 확장자 추가 시 누락 방지.

### Thumbnail 컴포넌트 개선

- **Problem**: 이미지 렌더링과 아이콘 렌더링 로직이 Thumbnail 컴포넌트 하나에 혼재되어 유지보수가 어려웠다. virtual window 구현 시 뷰포트 밖에 있는 이미지까지 즉시 로드되어 불필요한 네트워크 요청이 발생했다.

- **Solve**: 단일 컴포넌트를 역할 기반으로 세 개로 분리했다 — 외부 URL 이미지 담당, SVG 아이콘 담당, 분기 로직 담당. `lazyLoad` prop을 추가하여 virtual window 환경에서 뷰포트 진입 시점에 이미지를 로드할 수 있도록 했다. 기존 lazy load 훅을 재사용하여 중복 구현 없이 기능을 확장했다.

- **Result**: 각 내부 컴포넌트를 독립적으로 수정 가능. 불필요한 이미지 로드 제거로 네트워크 성능 개선.

### ConfigProvider — 디자인 시스템 다국어 지원

- **Problem**: 컴포넌트 내부 텍스트(버튼 레이블, 빈 상태 안내문 등)가 하드코딩되어 다국어 서비스에 적용할 수 없었다. 디자인 시스템에 i18n 라이브러리를 직접 내장하면 각 앱의 의존성 버전과 충돌할 우려가 있었다.

- **Solve**: React Context 기반 `ConfigProvider`를 설계하여 디자인 시스템이 특정 i18n 솔루션에 의존하지 않도록 했다. 각 앱이 자신의 i18n 솔루션으로 번역한 텍스트 객체를 `ConfigProvider`에 주입하면, 하위 컴포넌트가 Context에서 번역 텍스트를 읽는 구조다. 기본값으로 영문 텍스트를 fallback으로 제공해 `ConfigProvider` 없이도 동작하도록 했다. 스페인어·일본어·포르투갈어 지원 확장 시 앱 쪽 로케일 설정 파일 수정만으로 대응 가능한 구조를 초기에 확보했다.

- **Result**: 앱이 자체 i18n 솔루션을 자유롭게 유지하면서 디자인 시스템 컴포넌트 텍스트를 커스터마이징 가능. 초기 설계의 확장 구조 덕분에 언어 추가 시 디자인 시스템 내부 수정 비용 최소화.

### Brand Logo SVG 컴포넌트

- **Problem**: 이미지 파일 기반 로고는 CSS로 색상 변경이 불가해 다크모드 대응을 각 서비스가 각자 방식으로 처리하고 있었다. 로고 이미지 파일이 서비스별로 분산 관리되어 브랜드 리뉴얼 시 일관성 유지가 어려웠다.

- **Solve**: 엠블럼과 로고타입을 SVG 인라인 컴포넌트로 개발하여 `currentColor`를 활용해 CSS `color` 속성만으로 색상을 제어할 수 있도록 했다. `variant`·`opacity` 등 커스터마이징 props를 지원하고, 레거시 이미지 기반 컴포넌트를 제거했다.

- **Result**: 다크모드를 포함한 브랜드 표현의 일관성 확보. 서비스에서 이미지 파일 개별 관리 불필요.

## 주요 구현 — 디자인 시스템 v2

v3 리뉴얼 프로젝트를 위해 디자인 시스템을 전면 재설계했다. 기존 v1 컴포넌트의 설계 경험을 바탕으로 API 일관성과 확장성을 높이는 데 집중했다.

**주요 구현 컴포넌트**: Badge 계열(Dot / Icon / Image / Counter / Label / Marker) / BasePopover / IconButton · IconToggle / Thumbnail · FileExtension / BreadCrumbs / ColorwaySelect / MenuListItem / BaseDropdown 등

### Badge 계열 컴포넌트

- **Problem**: 뱃지가 위치·콘텐츠 타입에 따라 서로 다른 컴포넌트 이름과 props 구조로 분산되어 있어, 디자이너가 새 뱃지 타입을 요청할 때마다 어느 컴포넌트를 수정해야 할지 혼란이 있었다.

- **Solve**: `Badge` 네임스페이스 아래 여섯 가지 변형(Dot / Icon / Image / Counter / Label / Marker)을 통일된 네이밍 규칙과 props 인터페이스로 구현했다. 각 변형이 공통 기반 레이어를 상속하여 위치(`position`) 및 크기(`size`) 토큰을 공유하도록 설계했다.

- **Result**: 디자이너-개발자 커뮤니케이션 비용 감소. 신규 뱃지 타입 추가 시 패턴 재사용 가능.

### 비활성화 상태 아이콘 렌더 우선순위 버그

- **Problem**: `disabled` 상태에서 `disabledIcon` prop이 전달되어도 렌더되지 않고 기본 아이콘이 출력되는 버그가 있었다. 조건부 렌더 로직에서 `disabled` 여부를 먼저 체크하지 않고 기본 아이콘 prop을 먼저 참조하는 우선순위 오류였다.

- **Solve**: 조건부 렌더 로직의 평가 순서를 수정하여 `disabled` 상태일 때 `disabledIcon` 존재 여부를 먼저 확인하도록 변경했다.

- **Result**: 전체 디자인 시스템 사용처에서 disabled 상태 아이콘이 올바르게 표시됨.

### 드롭다운 아이콘 회전 및 선택 상태 동기화 버그

- **Problem**: 드롭다운 열림 상태에서 화살표 아이콘의 회전 방향이 반전되지 않고, 외부에서 선택 인덱스 state를 변경해도 드롭다운 내부 선택 상태와 동기화되지 않는 두 가지 버그가 동시에 존재했다.

- **Solve**: 아이콘 회전 CSS `transform`의 조건을 열림 상태와 직접 연결하고, 선택 인덱스를 controlled 모드(외부 state 우선)와 uncontrolled 모드(내부 state 사용) 양쪽에서 올바르게 동작하도록 수정했다.

- **Result**: 드롭다운 UX 일관성 확보.

## 회고 / 아쉬웠던 점

- **브랜치 전략의 한계**: `stable`·`release`·`develop` 3단계로 구성했으나, 컴포넌트 수가 40~50개로 늘어나면서 단일 develop 브랜치에서 여러 컴포넌트 작업이 충돌하는 일이 잦았다. 컴포넌트별 독립 브랜치와 feature flag 방식을 도입했다면 병렬 작업과 로컬 테스트가 더 용이했을 것으로 판단한다.

- **API 설계가 구현만큼 중요하다는 것**: 컴포넌트 작업을 반복하면서 "컴포넌트 소비자를 위한 API 설계"가 내부 구현만큼 중요하다는 것을 배웠다. `ConfigProvider`처럼 의존성 충돌을 피하면서 확장성을 확보하는 설계는, 초기에 올바른 추상화 레벨을 잡아두면 이후 언어나 기능 추가 비용이 최소화된다. 반대로 early optimization으로 과도하게 추상화하면 실제 사용 패턴과 어긋나 오히려 API가 복잡해지는 경험도 했다.

- **Base 추상화 레벨 결정**: 컴포넌트 설계 초반에 Base 레이어를 어느 수준까지 잡을지 팀 내 논의가 많았다. 실제 서비스 사용 패턴을 먼저 수집하고, 반복되는 공통점을 역방향으로 추출하는 방식이 top-down 추상화보다 더 실용적이라는 것을 배웠다.

- **Storybook의 이중 효과**: 문서화 도구로 도입했지만, Story를 작성하는 과정 자체가 컴포넌트의 엣지 케이스와 props API 설계 결함을 사전에 발견하는 테스트 역할을 했다. 문서 작성이 설계 검증 수단이 된다는 점에서 컴포넌트 개발 워크플로에 Storybook 작성을 필수 단계로 포함한 것이 장기적으로 품질 향상에 기여했다.
