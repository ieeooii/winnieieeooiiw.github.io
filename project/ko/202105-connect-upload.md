## 주요 구현

### Presentational/Container 패턴과 Redux Slice 도입으로 뷰·비즈니스 로직 분리

- **Problem**: 드래그 앤 드롭·리치 텍스트 에디터·파일 첨부·가격 설정 등 복잡한 입력 요소들이 다단계 폼 안에 혼재하면, 뷰 코드와 비즈니스 로직이 뒤엉겨 수정 범위를 예측하기 어려워진다. 또한 SCSS 모듈 방식은 파일이 많아질수록 스타일 유지보수 비용이 높아졌다.
- **Solve**: Presentational/Container 패턴으로 뷰와 비즈니스 로직을 분리. 도메인별 Redux Slice로 각 스텝 상태를 독립 관리하고, Flux 패턴으로 단방향 데이터 흐름 유지. Next.js SSR 환경의 상태 동기화는 `HYDRATE` 액션으로 처리. CSS-in-JS(Emotion.js)를 도입하여 스타일과 컴포넌트를 같은 파일에서 관리.
- **Result**: 뷰·로직 분리로 각 영역의 수정 범위 명확화, Emotion.js 기반 스타일 관리 체계 확립

### Redux Saga로 멀티스텝 폼 상태 독립 관리

- **Problem**: 드래그 앤 드롭 파일 첨부·리치 텍스트 에디터·가격 설정 등 복잡한 입력 흐름을 다단계 구조 안에서 안정적으로 관리해야 했다.
- **Solve**: Redux Slice + Saga 기반으로 각 스텝의 상태를 독립적으로 관리. 리치 텍스트 에디터는 글자 수 제한·onBlur 에러 상태 처리를 커스터마이징하고, 파일 타입 검증 유틸 함수를 공통화해 여러 업로드 영역에서 재사용.
- **Result**: 신규 업로드 플로우 전체 완성. 이후 Edit 페이지에도 동일 컴포넌트 재사용.

### 클라이언트 사전 검증으로 잘못된 3D 파일 서버 전송 차단

- **Problem**: 3D 의상 파일은 전용 바이너리 포맷이다. 파일 선택 시점에 포맷 이상·버전 호환성·중복 등록 여부를 클라이언트에서 미리 검증하지 않으면, 잘못된 파일이 서버까지 전송되어 불필요한 API 비용과 유저 대기 시간이 발생한다.
- **Solve**: 파일 바이너리를 직접 파싱해 내부 메타데이터(머티리얼 구조, 아바타 호환성, 생성일 등)를 추출. 파싱 실패(구버전 파일·손상 파일) 시 Saga `cancel` effect로 즉시 중단해 이후 API 요청 차단. 파일 타입별 중복 등록 검증을 차별화하여 의상 파일은 동일 파일 재등록을 허용하고 나머지 타입에만 중복 검증 적용. 아바타 파일은 파싱한 식별자를 기반으로 사전 정의된 preset 맵을 조회해 카테고리 초기값 자동 설정. 편집 모드에서 파일 교체 시 서버 응답 코드로 변경 불가·확장자 불일치를 구분해 각각 다른 에러 메시지 안내. 신규 등록과 편집 모드의 FormData 구성을 분리하여 편집 시 새로 추가된 파일만 전송하도록 최적화.
- **Result**: 잘못된 파일의 서버 전송 차단, 아바타 카테고리 자동 설정으로 유저 입력 단계 감소, 편집 시 불필요한 파일 재전송 방지

### 타입별 선택 규칙 맵핑으로 카테고리 선택 상태 관리

- **Problem**: 카테고리는 Garment·Fabric·Trim·Avatar·Scene 5가지 타입으로 나뉘며, 타입마다 최대 선택 수·상호 배타 규칙·제출 포함 여부가 달라 일관된 처리 로직을 설계하기 어려웠다.
- **Solve**: 카테고리 타입을 키로 하는 선택 상한 맵으로 타입별 선택 가능 수를 일괄 관리. Garment의 Single/Outfits는 상호 배타 처리를 reducer에 구현. Avatar의 Motion/Pose 중간 노드는 UI 표시용으로만 사용하고 제출값에서 제외하는 파생 상태를 selector로 분리. FormData 조립 전 중복 id를 제거하는 방어 로직 추가.
- **Result**: 타입별 선택 규칙이 맵 기반으로 선언적 관리, 제출 로직과 UI 로직 분리

### RTL 행위 주도 테스트로 업로드 플로우 회귀 방지

- **Problem**: 업로드는 서비스 핵심 기능인 만큼 파일 첨부·드래그 앤 드롭·카테고리 변경·가격 옵션 등 전체 플로우가 정상 동작하는지 검증이 필요했으나, 테스트 코드가 전무해 회귀 버그 위험이 높았다.
- **Solve**: Jest + React Testing Library로 약 80개 테스트를 작성해 컴포넌트 단위 및 플로우 시나리오를 단계적으로 커버. `data-testid` 기반으로 쿼리를 정비하고, `screen` API 기반의 최신 RTL 패턴으로 통일.
- **Result**: 행위 주도 테스트 코드 작성 및 테스트 커버리지 70% 달성.

## 회고 / 아쉬웠던 점

컴포넌트 개발 전 재사용 범위를 먼저 파악하고 공용 컴포넌트로 설계한 것은 이후 유지보수 비용을 낮추는 데 효과적이었다. 레이아웃·태그·텍스트 입력·토스트 등 UI 원자 단위 컴포넌트를 공통화해 폼 전 영역에 일관된 스타일을 적용한 것도 이 작업의 핵심이었다.

카테고리 데이터 구조에 대해서도 아쉬움이 남는다. 당시 서버에서 트리 구조로 내려오는 데이터를 그대로 다루다 보니 중첩 탐색으로 인한 성능 문제가 발생했는데, 애초에 flat 배열로 설계했다면 더 나았을 것이다. 지금 돌아보면 `Map`으로 `id → node`를 O(1)로 참조하는 flat → tree 변환 로직을 구현했다면 O(n²) 중첩 탐색 없이 O(n)으로 처리할 수 있었을 것이다.

테스트 코드는 구현 세부사항에 의존하는 방식으로 작성해 리팩토링할 때마다 테스트가 깨지는 문제가 반복됐다. RTL의 핵심은 사용자 행위 기반 검증임을 이후에 깨달았고, 내부 구현이 아닌 사용자 관점의 인터랙션을 기준으로 테스트를 설계했어야 했다.
