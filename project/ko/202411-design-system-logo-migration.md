# 디자인 시스템 Logo 컴포넌트 마이그레이션

| 항목 | 내용 |
|------|------|
| 회사 | CLO Virtual Fashion |
| 카테고리 | SaaS |
| 서비스 | CLO-SET |
| 기술 스택 | Next.js, TypeScript, Emotion, @closet-design-system/core |
| 개발 기간 | 2024.11 |
| 서비스 링크 | style.clo-set.com |

## 소개

서비스 전체에 산재한 레거시 `CLOSETLogo` 컴포넌트를 디자인 시스템의 신규 `Emblem/Logo` 컴포넌트로 일괄 교체했다. 단순한 find & replace가 아니라, **플랜별 variant 시스템**(`free` / `pro` / `enterprise`)이 embed viewer · multiview 등 특수 렌더링 컨텍스트에서도 올바르게 적용되는지 케이스별로 검증하며 교체했다. 마이그레이션 완료 후 레거시 컴포넌트를 완전히 제거하여 디자인 시스템 단일 진실 공급원(SSoT)을 확립한 작업이다.

## 주요 구현

### 플랜별 Variant 시스템 연동

- **Problem**: 신규 `Emblem/Logo` 컴포넌트는 `free` / `pro` / `enterprise` 세 가지 variant를 지원하여 플랜에 따라 로고 디자인이 달라진다. 기존 `CLOSETLogo`는 단일 디자인이었기 때문에, 단순히 컴포넌트 이름만 바꾸면 플랜 정보를 전달하지 않아 모든 사용자에게 동일한 로고가 표시되는 문제가 발생한다. 특히 embed viewer처럼 인증 컨텍스트가 없는 환경에서는 플랜 정보를 별도로 주입해야 했다.
- **Solve**: 각 사용처에서 현재 유저의 플랜 타입을 가져오는 방식을 분석하여 (플랜 조회 훅 또는 컨텍스트별 플랜 데이터), variant 값을 올바르게 매핑. embed viewer처럼 인증 세션이 없는 환경에서는 컨텍스트에서 별도 주입된 플랜 정보를 활용하여 로고 variant 결정. multiview 등 특수 컨텍스트에서는 컨텍스트별 플랜 조회 방식에 맞게 각각 처리.
- **Result**: 모든 사용처에서 플랜에 맞는 로고 variant 정확히 표시

### Grep 기반 전수 조사 및 완전 제거

- **Problem**: `CLOSETLogo` 컴포넌트가 서비스 전체 어디에 사용되고 있는지 파악하지 않고 마이그레이션하면 누락 사용처가 생긴다. 특히 indirect import(re-export를 통해 사용하는 경우)나 동적 import 구문은 단순 텍스트 검색으로 놓칠 수 있었다.
- **Solve**: `grep -r "CLOSETLogo"` 및 `grep -r "closet-logo"` 로 전체 코드베이스를 스캔하여 사용처 목록 확보. import 경로가 다른 케이스(절대 경로 / 상대 경로 / barrel export)도 모두 포함하여 확인. 교체 후 재스캔하여 잔존 사용처 Zero 확인 후 레거시 컴포넌트 파일 삭제.
- **Result**: 레거시 컴포넌트 완전 제거, 이후 로고 디자인 변경 시 디자인 시스템 단일 수정으로 전체 반영 가능한 구조 확립

### 특수 컨텍스트 케이스별 검증

- embed viewer: iframe 내부에서 동작하므로 인증 세션 없이 컨텍스트별 플랜 데이터로 variant 결정
- multiview: 여러 콘텐츠를 동시에 보여주는 페이지로, 동일 사용자의 로고가 여러 인스턴스에서 렌더링될 때 variant가 일관되게 적용되는지 확인
- 각 케이스를 스테이징 환경에서 직접 확인하여 시각적 회귀 없이 마이그레이션 완료

## 회고

마이그레이션 작업은 "기능 개발"이 아니라는 이유로 과소평가되기 쉽지만, 실제로는 기존 컴포넌트의 **모든 사용 맥락을 이해하고 신규 인터페이스로 정확히 매핑**해야 하는 작업이다. 특히 플랜별 variant처럼 기존 컴포넌트에 없던 속성이 추가된 경우, 단순 교체가 아니라 각 사용처의 비즈니스 로직을 파악하여 올바른 값을 주입해야 한다. 이 경험을 통해 **컴포넌트를 디자인 시스템으로 이전할 때는 인터페이스 차이를 먼저 명세하고, 사용처별 차이점을 목록화한 뒤 순차적으로 검증**하는 프로세스가 필요하다는 것을 배웠다.
