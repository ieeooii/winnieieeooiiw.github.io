# 그래픽 소프트웨어 → 플랫폼 직접 파일 업로드 기능 개발

| 항목 | 내용 |
|------|------|
| 회사 | CLO Virtual Fashion |
| 카테고리 | SaaS |
| 서비스 | CLO-SET |
| 기술 스택 | Next.js, React.js, TypeScript, MobX, Emotion.js, SCSS, jQuery, Jest, Enzyme |
| 개발 기간 | 2020.07 ~ 2020.11 |
| 인원 | 프론트엔드 1, 그래픽 엔지니어 1, 백엔드 1, 프로덕트 디자이너 1 (프론트엔드 담당) |
| 서비스 링크 | [style.clo-set.com](https://style.clo-set.com) |

## 소개

CLO 소프트웨어에서 작업한 3D 의류 파일(`.zprj`, `.zpac` 등)을 CLOSET에 직접 업로드하는 기능이다. 파일 선택 → 스타일 아이템 매핑 → 어셈블리 그룹핑 → 렌더링 설정의 멀티 스텝 플로우로, 여러 3D 파일을 한꺼번에 처리하고 각 파일이 어떤 스타일 아이템에 속하는지를 사용자가 직접 매핑하는 구조다. 여러 파일 병렬 업로드 및 실시간 진행률 표시, 파일 타입·크기·해상도·파일명 클라이언트 사전 검증, 전역 드래그 앤 드롭 지원을 포함한다.

## 주요 구현

### FormData 기반 메타데이터 동반 파일 전송 파이프라인 구축

- **Problem**: CLO/MD 소프트웨어에서 내보낸 3D 원시 데이터를 웹 플랫폼에서 처리하려면 클라이언트-서버 간 파일 전송 규격을 새로 정의해야 했다. 소프트웨어의 파일 포맷과 플랫폼의 콘텐츠 데이터 모델이 달라, 메타데이터 매핑·파일 타입 분류·렌더링 옵션 전달 방식을 백엔드와 함께 설계해야 했다.
- **Solve**: 백엔드 엔지니어와 파일 전송 규격 및 API 인터페이스를 공동 설계. 클라이언트에서 파일과 스타일 번호·렌더링 옵션·그룹 정보 등 메타데이터를 함께 FormData로 구성해 전송하고, 서버가 이를 처리하여 플랫폼 콘텐츠로 변환하는 파이프라인을 구축.
- **Result**: CLO/MD 소프트웨어 작업물을 플랫폼에 직접 연결하는 엔드-투-엔드 업로드 파이프라인 완성

### jQuery → React.js 마이그레이션

- **Problem**: 직접 업로드 페이지가 jQuery 기반으로 구현되어 있어 명령형 DOM 조작이 코드 전반에 퍼져 있었다. 상태 관리가 DOM 상태에 암묵적으로 의존하는 구조라 기능 추가 시 부수 효과를 예측하기 어려웠고, React 기반 공통 컴포넌트·MobX 상태 관리·TypeScript 타입 안전성을 적용할 수 없었다.
- **Solve**: 페이지 전체를 React.js 컴포넌트 구조로 재작성. 상태 관리를 MobX로 전환하고, 기존 jQuery DOM 조작 로직을 선언적 React 방식으로 교체.
- **Result**: React 공통 컴포넌트·MobX·TypeScript 적용 기반 마련, 이후 기능 추가 및 리팩토링이 예측 가능한 구조로 전환

### 상태 머신 패턴으로 멀티 스텝 플로우 분기 최소화

- **Problem**: 각 스텝별로 허용하는 분기(3D 업로드 / 터테이블 업로드 / 빈 아이템 생성)가 달라 boolean 플래그 여러 개로 현재 스텝을 관리하면 조합 폭발 문제가 생긴다. 스텝 전환 시 이전 스텝 상태를 언제, 어느 범위까지 초기화해야 하는지도 명확하지 않았다.
- **Solve**: 현재 스텝을 단일 observable로 관리하고, 스텝별 렌더링할 컴포넌트를 객체 맵으로 선언하는 상태 머신 패턴 적용. 유효하지 않은 스텝 전환을 스토어 액션 내부에서 차단.
- **Result**: 스텝 전환 로직이 단일 상태값으로 집약되어 분기 최소화, 사용자 설정 유지로 반복 작업 부담 감소

### 파일별 Map 식별자 + computed로 동시 업로드 진행률 정확 추적

- **Problem**: 여러 파일을 동시에 업로드할 때 전체 진행률을 정확히 표시해야 한다. 단순히 전체 바이트를 하나의 카운터로 누적하면, 각 파일의 업로드 이벤트가 뒤섞여 진행률이 튀거나 부정확하게 집계된다.
- **Solve**: 파일마다 고유 식별자를 부여하고, 업로드 진행 이벤트를 수신할 때 해당 식별자를 키로 하는 맵(Map)에 현재 전송 바이트를 기록. 전체 진행률은 맵의 값을 합산하는 `@computed`로 자동 파생. Axios의 `onUploadProgress` 콜백으로 파일별 진행 이벤트를 개별 수신하여 맵을 갱신.
- **Result**: 파일별 진행 상태가 독립적으로 추적되어 동시 업로드 시에도 전체 진행률 정확히 표시

### 바이너리 헤더 파싱 포함 클라이언트 사전 유효성 검사

- **Problem**: 허용 파일 타입이 3D 파일·이미지·영상·문서 등으로 다양하고, 타입마다 크기 제한이 다르다(일반 최대 1GB, 영상 200MB, GIF 20MB). 확장자만으로는 실제 파일 포맷을 보장할 수 없고(특히 애니메이션 GIF/WebP), 이미지 해상도 초과나 파일명 특수문자 포함도 서버 처리 전에 차단해야 했다.
- **Solve**: 파일명 특수문자 검사, 타입별 크기 제한 비교, 이미지 해상도 검증을 업로드 전 클라이언트에서 수행. 애니메이션 여부는 파일 바이너리 헤더를 직접 읽어 판별. 검사 실패 시 해당 파일을 에러 유형과 함께 분류하여 사용자에게 구체적인 안내 표시.
- **Result**: 잘못된 파일이 서버에 전송되기 전 클라이언트에서 차단, 에러 원인별 명확한 안내 제공

### 그룹별 선택 상태 소유권 분리로 상태 오염 버그 해소

- **Problem**: 선택된 파일 목록·어셈블리별 그룹핑 구조·그룹 간 전환 시 선택 상태 초기화·auto-numbering 카운터를 단일 컴포넌트가 모두 관리하고 있었다. 상태 의존성이 뒤엉켜 그룹을 전환할 때 다른 그룹의 선택 상태가 오염되는 버그가 반복 발생했다.
- **Solve**: TypeScript로 전환하며 상태를 역할별로 분리. 어셈블리 그룹핑 로직을 별도 모듈로 추출하고, 그룹 전환 시 해당 그룹의 선택 상태만 초기화되도록 범위를 명확히 제한. "Keep current thumbnail" 체크박스 기능과 auto-numbering 툴팁 추가. 렌더링 설정 값은 localStorage에 저장하여 재방문 시 복원.
- **Result**: 그룹 전환 시 상태 오염 버그 해소, 상태별 책임 분리로 이후 기능 추가 시 수정 범위 예측 가능

### Enzyme으로 멀티 스텝 인터랙션 시나리오 행위 주도 테스트 구축

- **Problem**: 멀티 스텝 플로우에서 스텝 전환·파일 선택·에러 발생·그룹 전환 등 다양한 인터랙션 시나리오가 예상대로 동작하는지 자동으로 검증하는 수단이 없었다. 상태 조합이 복잡할수록 수동 테스트만으로는 회귀를 방지하기 어렵다.
- **Solve**: Enzyme으로 사용자 인터랙션 시나리오 단위의 행위 주도(behavior-driven) 테스트 코드 작성. 스텝 전환·에러 상태·그룹 전환 후 선택 상태 초기화 등 핵심 동작을 자동 검증하는 테스트 케이스 구성.
- **Result**: 주요 인터랙션 시나리오 자동화 테스트 확보, 이후 리팩토링 시 회귀 방지

### Emotion.js 마이그레이션으로 디자인 토큰 연동 및 접근성 개선 (2023.04)

- **Problem**: 업로드 컴포넌트가 SCSS 모듈로 스타일링되어 있어 디자인 시스템 토큰 적용이 불가능했다. 조건부 스타일링을 `className` 문자열 연결로 처리해 조건이 늘어날수록 코드 추적이 어려웠다. 콘텐츠명 입력 label이 잘못된 요소를 가리키는 접근성 버그도 있었다.
- **Solve**: Emotion.js 기반으로 전면 마이그레이션. 조건부 스타일은 `css` prop과 template literal로 처리하여 조건별 스타일이 명확히 파악되도록 수정. label `htmlFor` 속성 수정으로 접근성 버그 해소.
- **Result**: 디자인 시스템 토큰 적용 가능, 스타일 조건 추적 용이, 접근성 개선

## 회고

Direct Upload는 CLO 소프트웨어와 CLOSET 웹 서비스가 연결되는 접점이라 파일 포맷 변화나 렌더링 스펙 변경에 영향을 자주 받았다. 가장 큰 교훈은 상태의 "소유권"을 명확히 해야 한다는 것이다. 여러 상태가 하나의 컴포넌트에 혼재하면 어느 하나가 변경될 때 다른 상태에 의도치 않은 부수 효과가 생긴다. 이 경험 이후 "이 상태는 누가 소유하고, 언제 초기화되어야 하는가"를 먼저 설계하는 습관이 생겼다.
