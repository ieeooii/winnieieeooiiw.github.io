# 3D 엔진 API의 React 추상화 레이어 설계 및 뷰어 리뉴얼

## 소개

CLO-SET의 핵심 기능인 3D 뷰어를 전면 재구축했다. CLO3D 엔진을 React에서 사용할 수 있도록 추상화한 뷰어 엔진 패키지를 단독으로 설계·구현하고, 이미지 뷰어·3D 엔진 뷰어·렌더 뷰어·비디오 뷰어 등 다양한 뷰어 타입과 렌더 실행기·버전 관리·환경 설정 등 뷰어 전반의 기능을 담당했다.

엔진팀이 제공한 CLO3D API는 함수 목록만 나열된 형태로, 호출 순서나 React 연동 방식에 대한 정의가 없었다. 관련 정보가 여러 곳에 분산되어 있어 실제 개발보다 API를 파악하는 데 더 많은 시간이 걸렸다. 이를 그대로 앱에서 쓰면 엔진 사용법이 앱 코드 전반에 흩어지는 문제가 반복될 것이 명확했기 때문에, React 생명주기에 맞게 추상화한 hook 레이어를 독립 패키지로 설계했다.

## 주요 구현

### React StrictMode에서 canvas 이중 생성 문제

- **Problem**: React 18 StrictMode는 개발 환경에서 mount → unmount → mount를 의도적으로 두 번 실행한다. 이로 인해 엔진 init이 두 번 호출되어 canvas가 두 개 생기는 문제가 발생했다. 하나는 빈 canvas, 하나는 정상 렌더된 canvas가 DOM에 공존했다.
- **Solve**: 엔진 초기화 진입 시 기존 canvas를 먼저 제거하고 시작하도록 처리. 인스턴스가 이미 존재하면 재초기화를 막는 가드를 추가했다. 엔진 인스턴스는 hook 내부 state가 아닌 외부 핸들러로 관리해, unmount 시 cleanup → remount 시 재생성 흐름이 명확히 동작하도록 설계했다.
- **Result**: StrictMode 환경에서도 canvas가 단 하나만 렌더되고, 엔진 초기화/해제 사이클이 React 생명주기와 정확히 동기화됨.
- **Insight**: StrictMode를 끄는 것으로 해결하려는 유혹이 있었지만, 근본적인 설계로 해결한 것이 나중에 유지보수 면에서 큰 차이를 만들었다.

### 엔진 API를 React 생명주기 hook으로 추상화

- **Problem**: 엔진팀이 제공한 API는 함수 나열 형태로 사용 순서(초기화 → 데이터 로드 → 뷰어 옵션 적용)나 비동기 타이밍, 에러 처리 방식이 정의되어 있지 않았다.
- **Solve**: 패키지 구조를 세 가지 관심사로 분리했다 — 엔진 인스턴스 생성 및 canvas 마운트(초기화), 3D 파일 비동기 로드(콘텐츠 로딩), ResizeObserver + throttle로 canvas 크기 동기화(리사이즈). 각 기능을 역할별 hook으로 분리하고 공통 인터페이스로 통일했다. 뷰어 옵션(Avatar/Garment 표시, Strain Map, Exploded View, 확대경)을 각각 독립 hook으로 구현하고, 키보드 단축키도 별도 hook으로 분리했다. 에러는 엔진이 던지는 8가지 에러 타입을 구분해 처리. 이를 하나의 조합 hook으로 묶어 사용처에서는 단일 hook 호출만으로 엔진을 사용할 수 있도록 했다.
- **Result**: 사용처에서는 엔진 API를 직접 몰라도 hook만으로 모든 뷰어 기능을 사용 가능. 신규 뷰어 옵션 추가 시 인터페이스만 맞추면 되는 확장 구조 확보.

### Next.js SSR → Vite CSR 전환 결정

- **Problem**: 이전 앱은 Next.js 기반 SSR 구조였다. Datadog RUM 데이터를 분석한 결과, 글로벌 서비스 특성상 인도·중국 등 네트워크 환경이 열악한 지역에서 페이지 전환 시마다 서버 사이드 렌더링 지연이 누적되어 사용자가 체감하는 응답 간극이 컸다. 3D 뷰어처럼 이미 클라이언트에서 엔진을 실행해야 하는 경우 SSR의 이점이 크지 않은 반면, 서버 응답 대기 비용은 그대로 발생했다.
- **Solve**: 콘텐츠 앱을 Vite + React Router 기반 CSR SPA로 전환했다. 초기 HTML + 정적 자산을 CDN에서 바로 제공하고, 데이터는 클라이언트에서 직접 API를 호출하도록 변경. 정적 파일을 cloud storage에 업로드하고 CDN 엣지에서 서빙해 서버 왕복 없이 최대한 사용자 가까이에서 자원을 제공하도록 배포 구조를 설계했다.
- **Result**: 페이지 전환 시 서버 응답 대기 제거. 네트워크 환경이 느린 지역에서도 CDN 캐시 히트율을 높여 초기 자산 로딩 간극 감소.
- **Insight**: SSR의 SEO·초기 렌더링 이점이 필요한 페이지와, CSR이 더 적합한 상호작용 중심 페이지를 구분하는 것이 중요하다. 콘텐츠 뷰어처럼 인증 후 진입하는 페이지는 SEO 요건이 없고 클라이언트 상태가 무거워 CSR이 더 유리하다. 반면 SSR은 통합 로그인처럼 서버 단에서 API를 호출하거나 middleware에서 인증·리다이렉트를 처리해야 하는 경우, 클라이언트에 불필요한 의존성을 내려보내지 않아도 된다는 점에서 여전히 강점이 있다. 이번 CSR 전환은 그 트레이드오프를 인지한 상태에서 뷰어 앱의 특성에 맞게 내린 결정이다.

### 뷰어 엔진 패키지 — 소스 전용 배포 설계

- **Problem**: 패키지를 별도로 빌드해 배포하면 monorepo 내 타입 동기화가 복잡해지고, 소비 앱마다 트리쉐이킹이 제대로 적용되지 않는 문제가 생긴다.
- **Solve**: 빌드 스텝 없이 TypeScript 소스를 workspace 프로토콜로 직접 공유하는 소스 전용 패키지로 설계했다. `main`과 `types` 모두 `index.ts`를 가리키고, 소비 앱의 Vite 번들러가 실제 사용하는 hook만 트리쉐이킹해 가져가도록 위임했다. 3D 엔진 인스턴스와 React는 peer dependency로 선언해 소비 앱이 직접 제공하도록 강제, 패키지 자체가 런타임을 들고 다니지 않게 했다.
- **Result**: 별도 빌드·배포 없이 타입이 항상 최신 상태로 동기화. 소비 앱이 실제로 사용하는 hook만 번들에 포함.

### 뷰잉 옵션 hook 공통 인터페이스 설계

- **Problem**: Avatar 표시, Strain Map, Exploded View, 확대경 등 뷰잉 옵션이 늘어날수록 각 hook마다 반환 타입이 달라지면 UI 레이어의 구현 비용이 비례해서 증가한다.
- **Solve**: 모든 뷰잉 옵션 hook이 동일한 인터페이스를 반환하도록 통일했다 — 기능 존재 여부(`isExist`), 현재 활성 상태(`active`), 조작 불가 여부(`disabled`), `toggle`, `reset`. 단순 on/off가 아닌 다중 선택이 필요한 옵션에만 `select`를 선택적으로 추가해 확장성을 확보했다.
- **Result**: UI 컴포넌트는 hook 내부 구현을 알 필요 없이 동일한 인터페이스로 렌더링 가능. 신규 옵션 추가 시 인터페이스만 구현하면 기존 UI 재사용.

### 렌더 실행기 — 복잡한 워크플로우 단계별 분리

- **Problem**: 렌더 옵션(품질, 이미지 크기, 비디오/GIF), 프리셋 저장/불러오기, 렌더 서버 상태 표시, 렌더 취소 등 복잡한 워크플로우를 단일 UI에서 관리해야 했다.
- **Solve**: 렌더 관련 상태를 Jotai atom으로 중앙화하고, UI를 설정 → 실행 → 상태 모니터링 단계로 분리. 렌더 서버 상태는 socket으로 실시간 수신해 반영.
- **Result**: 복잡한 렌더 워크플로우를 단계별로 직관적으로 처리 가능.

### 턴테이블 이미지 시퀀스 재생

- **Problem**: 턴테이블(회전 애니메이션) 재생 시 이미지 시퀀스 로딩·재생 속도 제어·프레임 전환이 부드럽게 동작해야 했다.
- **Solve**: 이미지 시퀀스를 `requestAnimationFrame` 기반으로 제어하고, 사전 로딩(preload) 완료 후 재생 시작. 속도 슬라이더와 프레임 인디케이터 UI 연동.
- **Result**: 매끄러운 턴테이블 재생, 로딩 상태 피드백 제공.

### 컬러웨이 변경 후 뷰잉 옵션 복원

- **Problem**: 컬러웨이 변경 시 사용자가 설정한 뷰잉 옵션(strain map, pattern 등)이 초기화되는 버그.
- **Solve**: 컬러웨이 변경 시 현재 뷰잉 옵션 상태를 atom에 보존하고, 엔진 재초기화 완료 후 재적용.
- **Result**: 컬러웨이 변경 후에도 사용자 설정 유지.

### 리사이즈 중 렌더링 오류 방지 — 이중 리사이즈 전략

- **Problem**: 컨테이너 크기가 빠르게 변할 때 뎁스 피링(Depth Peeling) 기반 투명도 렌더링에서 정렬 오류가 발생했다. 단순 debounce만 적용하면 리사이즈 중 뷰어가 뭉개지고, 즉시 반영하면 렌더 오류가 생기는 트레이드오프가 있었다.
- **Solve**: ResizeObserver 콜백에 이중 전략을 적용했다. 짧은 throttle로 '빠른 리사이즈 모드'를 먼저 발행해 canvas 크기만 즉시 반영하고, 일정 시간 debounce로 정밀 리사이즈를 후행 발행해 최종 크기를 확정한다. 정밀 리사이즈 시에는 뎁스 피링 동기화를 위한 짧은 대기 시간을 추가로 두었다. window resize 이벤트 대신 ResizeObserver를 사용해 컨테이너 단위로 추적했다.
- **Result**: 리사이즈 중에도 렌더 오류 없이 canvas 크기가 자연스럽게 따라오고, 품질 렌더(뎁스 피링) 상태에서도 정상 동작.

### Vite 청크 분리 전략

- **Problem**: 모든 의존성을 하나의 vendor 청크로 묶으면 캐시 효율이 떨어지고, 반대로 모두 분리하면 HTTP 요청 수가 과다해진다.
- **Solve**: 무게와 변경 빈도 기준으로 selective manual chunk 분리를 적용했다. 3D 엔진, UI 스타일링, 데이터 페칭, 리치 에디터, React 코어를 각각 독립 청크로 분리해 앱 코드 변경이 vendor 청크 캐시를 무효화하지 않도록 경계를 그었다. 프로덕션 빌드 시 정적 파일은 cloud storage에 별도 업로드하고 base URL을 빌드 타임에 동적으로 주입해 CDN 캐싱 효율을 높였다. source map은 Datadog 에러 추적을 위해 프로덕션에서도 활성화했다.
- **Result**: vendor 청크는 배포 간 변경이 없으면 캐시를 그대로 재사용. 앱 코드 변경이 vendor 캐시에 영향을 주지 않음.

### 커스텀 i18n — Promise 캐싱 기반 Dictionary 패턴

- **Problem**: 범용 i18n 라이브러리는 기능 대비 번들 비용이 높고, URL 파라미터에서 언어를 추출해 동적으로 번역 파일을 로드하는 방식과 맞지 않았다.
- **Solve**: URL의 언어 파라미터를 읽어 해당 언어의 번역 JSON을 비동기 패치하는 커스텀 Dictionary 패턴을 설계했다. Map 기반 Promise 캐시를 도입해 같은 언어를 중복 요청하지 않도록 처리하고, 로딩 중에는 Suspense fallback을 보여주다가 완료 후 Context로 번역 값을 주입했다.
- **Result**: 불필요한 의존성 없이 필요한 기능만 구현. 언어 전환 시 캐시된 데이터를 즉시 재사용.

### 스크린샷 — 캔버스 합성 모듈

- **Problem**: 단순 `canvas.toBlob()`으로는 배경 색상, 로고 오버레이, 해상도 설정을 조합해 최종 이미지를 만들 수 없었다. 특히 SVG 로고는 CORS 제한으로 `drawImage()`에 직접 사용할 수 없었다.
- **Solve**: 오프스크린 canvas에 배경(단색 fill 또는 이미지 contain/fill 모드)을 먼저 그린 뒤 3D 뷰어 canvas를 합성. SVG 로고는 `Blob → ObjectURL` 변환 후 `drawImage()`로 오버레이해 CORS 오류를 우회했다. 해상도(배율), 품질, 포맷(png/jpg/webp)을 파라미터로 받아 조합 가능하도록 설계했다.
- **Result**: 배경·로고·해상도 조합을 자유롭게 설정해 고품질 스크린샷 다운로드 가능.

### 뷰어 엔진 상태 — 전역 접근과 아이템 전환 초기화

- **Problem**: 엔진 인스턴스와 뷰잉 옵션 상태는 툴바·설정 패널·뷰어 컨테이너 등 여러 컴포넌트에서 동시에 읽고 써야 한다. prop drilling으로 전달하기에는 계층이 너무 깊고, 단일 Context로 묶으면 불필요한 리렌더링 범위가 넓어진다.
- **Solve**:
  - **엔진 인스턴스를 atom으로 관리**: 엔진 인스턴스·뷰잉 옵션·로딩 상태·진행률을 atom 단위로 분리. 각 컴포넌트가 필요한 atom만 구독해 불필요한 리렌더링 억제
  - **atom 단위 reset 설계**: 아이템 간 이동 시 이전 엔진 상태를 깨끗하게 초기화할 수 있도록 각 atom에 reset 유틸리티를 함께 설계. 메모리 누수와 이전 상태 잔류 문제를 구조적으로 방지
  - **refetch 전략 보수화**: 탭 포커스 복귀·네트워크 재연결 시 자동 refetch를 비활성화. 이미 로드된 3D 데이터가 백그라운드에서 교체되면 안 되는 뷰어 특성에 맞게 설정
- **Result**: 컴포넌트 계층에 관계없이 atom 구독만으로 엔진 상태 접근 가능. 아이템 전환 시 이전 상태 잔류 없이 깔끔한 초기화.
- **Insight**: 뷰잉 옵션처럼 UI 인터랙션 상태는 Jotai가 적합했지만, 컴포넌트 외부(이벤트 핸들러, 모듈 레이어 등)에서 atom에 접근해야 할 때는 한계가 드러났다. 이런 케이스가 늘어난다면 외부 접근이 용이한 Zustand가 더 적합했을 것이다.

### 컴포넌트 설계 — 뷰어 타입 디스패처 패턴

- **Problem**: CLO-SET 아이템은 3D 파일·이미지·렌더링·턴테이블·기타 등 다양한 타입을 가진다. 단일 뷰어 컴포넌트에서 모든 타입을 처리하면 조건 분기가 중첩되고, 타입별 초기화 로직이 뒤섞여 유지보수가 어려워진다.
- **Solve**:
  - **타입 디스패처 패턴**: 최상위 뷰어 컴포넌트는 콘텐츠 타입만 판별하고, 실제 렌더링은 타입별 독립 컴포넌트에 완전히 위임. 각 타입 컴포넌트를 lazy로 분리해 필요한 시점에만 로드
  - **CLO3D 내 2차 분기**: 3D 타입 내에서도 3D 엔진 뷰·2D 패턴 뷰·이미지 뷰·렌더링 뷰를 URL 파라미터 기반으로 추가 분기. 뷰 전환이 라우트 변경이 아닌 쿼리 업데이트로 처리되어 레이아웃 리마운트 없음
  - **레이어 분리**: 데이터 패칭 컨테이너(API 호출·Suspense 담당) → 타입 판별 디스패처 → 엔진 props 조립 훅 → 실제 엔진 렌더링을 각 레이어로 분리. 각 레이어가 단일 책임만 가지도록 설계
  - **부분 에러 경계 래핑**: 각 뷰어 타입 컴포넌트를 독립 에러 경계로 래핑해 특정 뷰어 타입의 오류가 전체 페이지를 차단하지 않도록 격리
  - **isMounted 가드**: 3D 데이터 로드·컬러웨이 변경 등 비동기 작업 완료 후 컴포넌트가 이미 언마운트된 경우를 감지해 state 업데이트를 건너뜀
- **Result**: 타입별 코드가 완전히 격리되어 신규 뷰어 타입 추가 시 기존 코드 수정 없이 디스패처에 케이스만 추가. 각 타입의 에러가 독립 격리되어 부분 장애 시에도 다른 뷰어 기능은 정상 동작
- **Insight**: 디스패처 패턴은 타입이 늘어날수록 효과가 커지지만, 타입별 공통 로직(진행률 표시, 에러 UI 등)을 어느 레이어에 둘지 계속 결정이 필요했다. 공통 래퍼를 일찍 정의해두지 않으면 각 타입 컴포넌트에 같은 코드가 반복 추가된다.

### 렌더링 최적화

- **Problem**: 3D 뷰어 페이지는 엔진 초기화·대용량 3D 파일 로드·다수의 뷰잉 옵션 컴포넌트가 동시에 렌더되어 초기 번들 크기와 메모리 사용이 모두 문제였다.
- **Solve**:
  - **뷰어 타입별 코드 스플리팅**: 3D 뷰어·이미지 뷰어·렌더 뷰어·턴테이블 뷰어를 각각 lazy 분리해 초기 번들에 포함하지 않음. 설정 오버레이·뷰잉 옵션 패널 등 보조 UI도 lazy 분리
  - **React Query 캐시 전략**: 3D 데이터를 아이템 ID + 버전 복합 키로 캐싱해 같은 버전 재방문 시 네트워크 요청 없이 즉시 렌더. 뷰어 메타데이터는 단기 staleTime으로 반복 요청 최소화
  - **엔진 리소스 명시적 해제**: 페이지 이동 시 엔진 인스턴스의 dispose API 호출 후 canvas DOM 노드를 직접 제거. React unmount만으로는 GPU 리소스가 해제되지 않는 엔진 특성을 명시적 cleanup으로 보완해 메모리 누수 방지
  - **ResizeObserver 기반 크기 추적**: `window.resize` 이벤트 대신 ResizeObserver를 사용해 뷰어 컨테이너 크기 변화만 감지. 뷰어와 무관한 다른 요소의 리사이즈가 엔진 업데이트를 트리거하지 않도록 범위 한정
  - **초기값 ref 고정**: 뷰어 초기 렌더 시점의 컬러웨이 인덱스 등 초기값을 ref로 고정해 외부 상태 변화에 의한 effect 재실행을 방지
- **Result**: lazy 분리로 초기 번들에서 뷰어 코드 제외, 페이지 이동 후 GPU 메모리 누수 없음, 불필요한 엔진 리사이즈 호출 제거
- **Insight**: 3D 엔진처럼 React 외부의 리소스를 다룰 때는 React의 unmount만 믿지 않고 명시적인 cleanup을 직접 설계하는 것이 안전하다. GPU 메모리 누수는 DevTools에서 즉시 드러나지 않아 뒤늦게 발견하기 쉽다.

## 회고 / 아쉬웠던 점

가장 오래, 가장 넓은 범위로 기여한 프로젝트다.

엔진팀이 제공한 API를 컴포넌트에 직접 모두 노출하는 대신, 기능 단위 hook으로 추상화해 사용처에서 필요한 API만 호출되도록 설계한 것이 이 프로젝트의 핵심이었다. 덕분에 엔진 API가 앱 코드 전반에 흩어지지 않고, hook 인터페이스만 알면 엔진 내부 구현 없이도 기능을 조합할 수 있는 구조가 만들어졌다.

개발 중반에 기존 디자인 시스템을 전면 폐기하고 전사 프론트엔드가 함께 구축한 회사 공통 디자인 시스템으로 일괄 마이그레이션하는 결정이 내려졌다. 예상치 못한 전면 교체였고, 뷰어 전반의 UI 컴포넌트를 신규 디자인 시스템 기준으로 재구성하면서 프로젝트 기간이 연장됐다. 변경 범위를 빠르게 파악하고 우선순위를 재조정하는 것이 기술적 구현만큼 중요하다는 것을 체감했다.

앱에 CSR(Vite)을 처음 도입한 프로젝트이기도 한데, SSR과 CSR의 트레이드오프를 단순한 기술 선호가 아닌 Datadog RUM 데이터를 근거로 결정한 경험이 인상적이었다. CSR은 초기 로드가 느리다는 단점이 있지만, 이후 페이지 전환 속도·인터랙션 응답성 등 다른 지표들은 훨씬 개선됐다. 측정 기반으로 아키텍처를 결정하는 것이 설득력 면에서도, 이후 회고 면에서도 훨씬 명확하다는 것을 실감했다.
